# 开发与可读性约束

后端业务按 `internal/modules/<业务模块>` 划分。模块内部按用途维护 DTO、服务依赖、查询和业务动作。`internal/business/service.go` 只组装模块，跨模块业务验收放在该目录的集成测试中。

## 手写代码

- 一个语句占一行；结构体字段与 DTO 转换逐项列出。
- 函数之间留空行。
- 前置校验、查询、状态判断、数据修改、审计通知和返回按逻辑分段。
- `if`、`for`、`switch` 等控制块结束后，后续逻辑留空行。
- 长 Ent 调用链逐行组织；多个筛选条件在参数列表内逐项列出。
- 变量名称表达业务含义，例如 `userID`、`version`、`assignmentRecord`、`amount`、`client`、`err`。
- 不把同一项业务拆成没有职责意义的极小函数，也不把不相关业务塞在同一文件。

`gofmt` 处理语法格式；`scripts/check-go-style.go` 检查函数展开、函数间空行和控制块后的分段。业务逻辑是否清晰仍需审查。

## 验证

在仓库根目录运行：

```powershell
./scripts/check.ps1
```

该命令运行可读性检查、Go 全量测试、`go vet`、进程入口构建、管理后台格式/测试/构建及小程序纯 JS 单元测试。小程序测试使用模拟微信接口，不代表开发者工具或真机联调。缓存置于被忽略的仓库 `tmp/` 目录，避免依赖机器上的其他用户缓存权限。

集成测试使用 `.env` 中的本机 PostgreSQL 连接参数，每个测试创建独立 `btyx_test_` schema 并在结束时清理，不修改 `public` 或应用 schema 的数据。

`backend/ent/` 下除 `schema/` 与 `generate.go` 外均为生成代码，不手动重排或修改。模型更改后重新生成。

## 用户数据表

用户子表通过 `user_id` 关联 `users.id`。微信注册创建基础账户和微信身份。认证、平台和报名资料在对应流程首次提交时写入。

| 表 | 负责的数据 |
| --- | --- |
| `users` | 昵称、头像文件 ID、领取资格和软删除标记 |
| `wechat_identities` | 微信 OpenID 与本系统用户 ID 的唯一关联 |
| `user_verifications` | 加密的报名实名资料及微信验证手机号 |
| `user_platform_profiles` | 当前抖音和小红书账号 |
| `user_enrollments` | 每次报名独立保存账号、证件、联系方式、审核决定和标签。同一用户最多有一条当前报名 |
| `consents` | 用户确认过的协议版本及签署时间 |
| `sessions` | 登录会话哈希、角色及有效期 |

升级旧版时，先停止使用旧字段的进程并备份目标 schema，再运行独立 Ent 迁移。迁移会在一个事务中复制用户领域数据并移除对应旧列，用户 ID、会话和协议签署记录沿用原值。
